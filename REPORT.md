Опис проекту

У другій практичній роботі проект було розширено низькорівневими механізмами обробки даних. До системи обліку студентів додано симуляцію апаратних портів введення-виведення (матриця 16x16) та інтегровано роботу з масивами для оптимізації зберігання оцінок. Також реалізовано систему логування операцій з використанням оптимізованої обробки рядків.



Завдання

1\.	Поясніть різницю між одновимірними та двовимірними масивами. Наведіть приклади використання в роботі.



* Одновимірні масиви: Це лінійна структура, де елементи йдуть один за одним. Доступ здійснюється за одним індексом.

Приклад у роботі: Масив byte\[] labGrades у класі Student для зберігання оцінок за 10 лабораторних робіт.



* Двовимірні масиви (матриці): Це таблична структура (рядки та стовпці). Доступ здійснюється за двома індексами \[row, col].

Приклад у роботі: Port\[,] matrix у класі PortMatrix для створення сітки 16x16, що імітує фізичне розташування портів.



2\.	Чому StringBuilder ефективніший за звичайну конкатенацію? Продемонструйте на прикладі з PortLogger.



Звичайні рядки (string) в C# є незмінними (immutable). Кожна операція + створює новий об'єкт у пам'яті, що при великій кількості записів призводить до значних витрат ресурсів.



StringBuilder використовує внутрішній буфер, який динамічно розширюється, не створюючи нових об'єктів при кожному додаванні тексту.



Приклад з PortLogger: При формуванні повного логу операцій (GetFullLog), де записів може бути сотні, використання StringBuilder дозволяє миттєво зібрати текст, тоді як конкатенація через + викликала б помітні затримки ("фрізи") програми.



3\.	Як ви реалізували симуляцію портів вводу/виводу? Які масиви використовували?



Симуляція реалізована як програмна модель "заліза".

Реалізація: Створено клас Port, який містить статус (відкритий/закритий) та буфер даних.

Масиви: Використано двовимірний масив об'єктів класу Port (Port\[16, 16]) та одновимірні масиви байтів (byte\[]) для передачі та зчитування даних через буфери портів.



4\.	Як інтегрували масиви в already існуючу систему управління студентами?



Масиви були інтегровані в клас Student для заміни розрізнених змінних оцінок. Це дозволило:

Автоматизувати розрахунок середнього балу через цикл for.

Додати функціонал клонування (Clone()), де масив оцінок копіюється як окрема сутність (глибоке копіювання), щоб клон не залежав від оригіналу.



5\.	Опишіть логіку роботи з матрицею 16×16.



Матриця представляє собою адресний простір з 256 портів.

1)Звернення до порту відбувається через координати рядка (0–15) та стовпця (0–15).

2)Реалізовано методи WriteToPort та ReadFromPort, які працюють з масивами байтів, імітуючи низькорівневу передачу пакетів даних.

3)Метод FindOpenPorts сканує всю матрицю двома вкладеними циклами для виявлення активних підключень.



6\.	Які труднощі виникали при роботі з масивами та як ви їх вирішили?



Труднощі: Виникнення помилок при спробі використати методи LINQ (наприклад, .Average()) на масивах byte без попереднього приведення типів (помилка CS1929).



Вирішення: Використано .Select(v => (double)v) для перетворення значень перед обчисленням середнього арифметичного. Також виправлено логічні помилки в структурі switch-case, де відсутність закриваючих дужок блокувала компіляцію проекту.



7\.	Порівняйте масиви з колекціями (List<T>). У яких випадках ви свідомо обрали масиви?



Масиви: Обрані для PortMatrix та оцінок лабораторних, оскільки розмір цих структур строго зафіксований техзавданням (16x16 та 10 робіт). Масиви швидші та займають менше пам'яті.



List: Використано для загального списку студентів у групі, оскільки їхня кількість динамічна (ми можемо додавати або видаляти студентів під час виконання програми).



8\.	Що нового ви дізналися під час виконання роботи?



Під час роботи я навчився реалізовувати інтерфейс ICloneable для створення точних копій об'єктів, працювати з багатовимірними масивами об'єктів та оптимізувати роботу з текстовими даними за допомогою StringBuilder. Також я закріпив навички роботи з Git, використовуючи систему feature-гілок для кожної окремої задачі.

Для організації процесу розробки було використано модель GitFlow. Репозиторій містить 9 гілок, кожна з яких виконує свою роль:

main — основна стабільна гілка з фінальною версією проєкту (реліз v2.0).

develop — головна гілка розробки, куди зливалися всі реалізовані функції перед фінальним релізом.

7 Feature-гілок (тематичні гілки для окремих завдань):

feature/student-lab-grades — реалізація роботи з одновимірними масивами (оцінки студентів).

feature/port-class — створення базової структури класу Port.

feature/port-matrix — реалізація логіки двовимірного масиву (матриця портів 16×16).

feature/stringbuilder-logger — впровадження класу PortLogger з використанням StringBuilder для оптимізації роботи з рядками.

feature/menu-integration — розробка інтерактивного консольного меню та об'єднання всіх модулів.

feature/persistence — додавання функціоналу для збереження та завантаження стану системи.

feature/refactoring — фінальна чистка коду, виправлення помилок (зокрема CS0136) та форматування за стандартами .NET.

Такий підхід дозволив ізольовано розробляти кожен модуль програми, мінімізувати конфлікти в коді та зберегти чітку історію змін, що відображено на згенерованому графіку git log.
